# 重新設計:用手機鏡頭直接點出庫存

## 1. 目標

盤點人員拿手機對著貨架,畫面上就標出每一件商品並算出數量,人只處理例外。

## 2. 原設計為什麼達不到

原流程是「拍照 → 上傳 → 等結果 → 逐項核對數字」。問題不在辨識速度,而在**結果無法驗證**:畫面只給一串數字,人無從判斷 AI 數對沒有,只能自己重數一次,等於沒省力。數字錯了也不知道錯在哪一件。

## 3. 新設計的核心:讓數量看得見

**每一件商品在畫面上標一個點,點數就是數量。**

- 一眼就能看出漏標哪一件、多標哪一件、哪一件標錯商品。
- 修正是「點一下」,不是輸入數字:點圓點刪除,點空白處補上。
- 人做的是「看」而不是「數」。這也是對注意力最友善的做法:不用在腦中維持計數。

## 4. 流程(第一階段,已實作)

```
開始即時點貨
   │
   ▼
即時取景 ──(手機拿穩約 1 秒,畫面幾乎不動且不是全黑)──▶ 自動定格(震動提示)
   ▲                                                        │
   │                                                        ▼
   │                                       送出辨識,要求回傳每一件的位置
   │                                                        │
   │                                                        ▼
   │                               定格畫面上疊圓點(每種商品一個顏色)
   │                               點圓點=刪除;點空白=補到選取的商品
   │                               「每點 ×N」處理後排深度
   │                                                        │
   └────────────── ✓ 全部計入,下一格 ◀──────────────────────┘
```

設計重點:

| 設計 | 理由 |
|---|---|
| 拿穩自動定格,不用按快門 | 少一個動作;按快門本身會晃動。另有「立即定格」按鈕備用 |
| 定格後手機可以放下來 | 不需要一直舉著對準 |
| 一格一格盤,不是邊走邊錄 | 邊走邊錄需要跨畫面追蹤同一件商品,重複計算的風險高(見第 7 節) |
| 計入後自動回到取景 | 形成「對準 → 看 → 計入 → 下一格」的節奏,不用回想下一步 |
| 辨識失敗或沒設定後端仍可手動點 | 變成一個「點一下算一件」的計數器,不會卡住 |
| AI 沒回傳位置時退回數字 | 顯示「另有 N 件 AI 未標位置」,用 − + 調整 |

## 5. 視覺方法的物理極限,以及對策

相機只看得到正面。這不是模型能力問題,任何視覺方法都一樣。

| 情況 | 對策 |
|---|---|
| 後排被前排擋住 | **每點 ×N**:每個商品記住一個「深度」(前後幾件)。可見件數 × 深度 = 數量。只在貨架補滿時準確,沒補滿要人工判斷 |
| 整箱封著 | 點箱數,用「每點 ×N」填每箱入數 |
| 堆疊雜亂、看不清 | 先整理再拍,或改用手動輸入 |
| 相似口味 | 圓點顏色不同,標錯一眼可見;混淆紀錄會成為下次的提示 |

學習記憶記錄的是「可見件數」的修正,**不含深度**,避免把看不見的庫存當成辨識錯誤。

## 6. 技術做法

- **穩定度偵測**(手機端):每 150 毫秒把畫面縮成 32×24 灰階,比較前後兩格的平均差。差異夠小、畫面對比足夠(排除鏡頭被遮住),連續約 0.9 秒就定格。
- **位置回傳**:請求帶 `points: true`,後端在 user 訊息加上「為每個可見單位回傳中心點座標(0–1000 的比例值)」的指示。這段放在快取斷點之後,**不影響提示詞快取,也不影響原本的拍照模式與既有評測**。
- **座標處理**:超出範圍的夾回邊界,格式錯誤的丟棄;有回傳位置時以點數為準。
- **成本**:每個點約多 8 個輸出 token,50 件約多 400 token。

## 7. 路線圖:從「定格辨識」到「真正即時」

| 階段 | 做法 | 即時性 | 前提 |
|---|---|---|---|
| **1(已實作)** | 自動定格 + 雲端辨識回傳位置 + 點擊修正 | 定格後等幾秒 | 無,現在就能用 |
| **2** | 手機端執行「不分品項的商品偵測模型」(以密集貨架資料集訓練的偵測器,轉成可在瀏覽器執行的格式),即時在畫面上框出每一件並計數;品項辨識仍交給雲端,每種只送一次 | 取景時就看得到框與數量 | 要找到或訓練合適的模型,並實測中階手機的速度 |
| **3** | 用累積的修正資料訓練自己的品項模型,全部在手機端完成 | 完全即時、可離線 | 要先保存照片與修正結果(需 NAS 儲存空間與同意) |
| **4** | 邊走邊錄,跨畫面追蹤去重 | 連續掃描 | 技術難度最高,放最後 |

階段 1 的點擊修正,正好就是階段 3 需要的標註資料。目前**還沒有保存照片與點位**,要做階段 3 得先加上這一步。

## 8. 驗證狀態

### 8.1 程式流程(自動化測試)

`test/live.test.js`,29 項,假鏡頭 + NAS 伺服器 + 模擬的 Claude:自動定格、請求內容、座標清理、畫面疊點、點擊刪除與補點、切換商品、深度相乘、未指定商品擋下、別名、計入與進度、學習紀錄、自動回到取景、無位置時退回數字、復原、誤報紀錄、辨識失敗後手動點、釋放相機。

### 8.2 真實貨架照片上的實測(2026-11-15)

**方法**:公開的貨架資料集(Varol & Kuzu 2014,`gulvarol/grocerydataset`,每件商品有人工標註的框),隨機抽 12 張(每張 10 到 43 件,共 279 件),縮到長邊 1600px。用與正式程式**完全相同的提示詞**(由 `_shared/count.ts` 產生),讓 Claude Sonnet 只憑看圖輸出結果。評分用 `eval/score_points.py`:每個點與標註框一對一配對。

| 測試 | 結果 |
|---|---|
| 標點模式的計數(12 張、279 件) | 12/12 張完全正確,總量誤差 0% |
| 點的位置 | 279 個點全部落在各自的商品上(命中率 100%、涵蓋率 100%);點離框中心的中位距離約為框寬的 3% |
| 對照:純數字模式 | 12/12 張完全正確。標點指示沒有讓計數變差 |
| 分品項(給 16 個品牌的清單,2 張、58 件) | 每一件都有被點到。第一張多標 2 點,都是露出一角的後排包裝,模型有在備註說明。人眼核對第一張 36 件:約 3 件品項標錯(相似包裝認錯品牌、一件標為看不清),其餘正確。第二張只核對了件數與位置(22/22),品項未逐一核對 |
| 端到端 | 把真實照片當成鏡頭畫面、真實的模型輸出當成後端回應,實際跑盤點程式:自動定格、疊點、各品項件數、點擊修正都正常 |

**這證明了什麼**:在整齊、正面朝外的貨架上,「每件標一個點」的做法成立,數量與位置都可靠。品項辨識大致正確但會出錯,而錯誤在畫面上以顏色呈現,可以一眼看到並點擊修正。這正是這個設計要解決的事。

**限制,請不要過度解讀**:
- 只有 12 張、同一個資料集、單一商品類型(小盒包裝、排列整齊、單層正面)。**不是你們倉庫的包裝食品**,袋裝、反光、疊放、混放的表現仍未知。
- 模型是透過 Claude Code 的子代理執行,不是正式的 API 呼叫:系統提示、圖片前處理、思考深度都可能與正式環境不同。子代理各自處理 3 到 6 張,不是每張獨立。
- 已排除抄答案:每個子代理的工具使用次數等於「讀指示 + 看圖 + 寫結果」,沒有多餘讀檔;點也不是剛好等於框中心。
- 第一張圖的品項核對是我(模型)看圖判斷,不是人工標註。

### 8.3 仍未驗證(需要你這邊的環境)

1. **正式 API 路徑**:用真實金鑰呼叫(含提示詞快取是否命中、實際費用)。這個開發環境拿不到可用的 API 憑證。
2. **你們倉庫的真實照片**:用 `run_eval.py --direct --points` 加 `score_points.py` 重複 8.2 的測試。
3. **真實手機**:自動定格的靈敏度(門檻是估計值)、手指點擊的準確度、不同手機的相機行為。4 層貨架在手機上圓點偏小,建議一次拍一到兩層。
4. 即時鏡頭需要 HTTPS。區網 HTTP 下只能用「拍照辨識」。
5. 已知小問題:顏色只有 8 種,超過 8 個品項時顏色會重複。

## 9. 判斷這個設計成不成立

跑評測時加 `--points`,用同一批照片比較:

- 標點模式的計數準確度不低於純數字模式,而且人眼看點位大致對得上 → 設計成立,繼續做階段 2。
- 點位偏移明顯,但計數準 → 仍可用,點當作視覺輔助;優先做階段 2 的手機端偵測來取代。
- 計數明顯變差 → 標點指示干擾了計數,改成兩階段(先數後標)或直接走階段 2。
